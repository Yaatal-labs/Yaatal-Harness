00 En une phrase

La thèse Yaatal est une plateforme d'IA souveraine, edge-vers-cloud, pour le commerce et l'assistance africains (wolof/français d'abord), conçue contraintes-d'abord — téléphones bon marché, réseaux faibles, batterie, parole code-mixée, peu de données, argent sensible à la confiance. Sa primitive fondatrice : les modèles proposent, l'Engine dispose — l'IA peut suggérer une action, mais seul l'Engine typé-souveraineté transforme l'intention en effet réel (argent, commandes, données personnelles), et les données Sovereign sont garanties à la compilation de ne jamais quitter le Sénégal. BOBO est la première surface applicative, pas la finalité.

01 L'architecture en couches — à lire en premier

Yaatal n'est pas un monolithe — trois couches plus une voie de R&D. Ce manifeste est la vue Engine (runtime) ; le Harness a la sienne. Dépendance à sens unique : l'Engine dépend du Harness, pas l'inverse.

APPS BOBO · YOKK · NJOOBA · DAARA UX produit & parcours [par app]
│ appelle HTTPS/JSON + JWT ← le SDK @yaatal/client vit ici [ROADMAP]
▼

│ invoque des contrats Rust en-process
▼

▼

R&D HARNESS — prouve / évalue / durcit, puis promeut —┐ [R&D]
(notebooks, entraînement, datasets — ne part PAS en prod) ┘
Dépendance

L'Engine fournit le contexte utilisateur/session/profil vérifié et appelle les pipelines du Harness via des contrats Rust explicites.

Frontières

Le Harness ne possède jamais auth/profil/transport/routes/déploiement. L'Engine ne possède jamais l'UX d'une app. Les apps ne dupliquent jamais la logique de fiabilité IA.

Promotion

Une app en a besoin → app. Deux apps → Engine. IA non prouvée → R&D Harness. Fiabilité IA prouvée → Runtime Harness.

Alignement en cours : le dépôt Engine garde ses propres copies des crates de capacités (ai, search, feed, voice). Cible : possédées par le Harness, consommées par l'Engine. Les collisions de noms + le sens de dépendance sont une tâche active, pas l'état final.

03 Directives primordiales

Frontières de couches

Apps / Engine / Harness, dépendance à sens unique. Empêche la plateforme de devenir trois systèmes concurrents ; les capacités sont prouvées en R&D et promues une fois durcies.

La souveraineté est un type, pas un réglage

La résidence au Sénégal / Diamniadio doit être incontournable. Dans le système de types, le compilateur est l'auditeur.

Économie & réseaux africains d'abord

Calcul facturé, bande passante chère/intermittente, appareils contraints. Préférer local/edge/bon-marché avant frontier/cloud ; se dégrader proprement.

Promotion plutôt que duplication

App → Engine → Runtime Harness est un cliquet à sens unique mérité par la preuve, pas le copier-coller. Rien de codé en dur dans Rust.

04 Manifeste des sous-systèmes — choix par choix

4.1

Loco — « Rust on Rails »

EngineV1
Quoi
Framework web Rust tout-en-un : routage, sea-orm, workers, mailers, auth JWT.
Pourquoi
Livrer du produit, pas de la plomberie, dans un langage sûr en mémoire, sans GC, à faible empreinte ; les types de Rust rendent possible la colonne souveraineté.
Écarté
Axum à partir de zéro (verbeux) ; Node/Python (empreinte, GC, garanties faibles).
N'est pas
Un essaim de microservices. Un binaire runtime unique.
4.2

Système de types de souveraineté

Cœur partagéV1
Quoi
Sensitivity { Sovereign · Operational · Public }, un SensitivityTag scellé, un Tagged<T,S> à type fantôme. Sovereign = reste dans le Postgres de Diamniadio, ne se réplique jamais vers l'edge.
Pourquoi
La résidence est un invariant de premier ordre ; le scellage transforme une mauvaise classification en erreur de compilation.
Écarté
Vérifications à l'exécution / drapeaux de config (contournables, dérive, échec ouvert).
N'est pas
Une case à cocher RGPD.
4.3

Stockage gardé par étiquette

Cœur partagéV1
Quoi
StorageDispatcher<T,S> sur memory · postgres · r2. R2 n'implémente que …<T,Public> — un Tagged<T,Sovereign> vers R2 ne compile pas.
Pourquoi
L'edge est Public par construction ; les données souveraines ne peuvent physiquement pas y être routées.
N'est pas
Un endroit d'où les données souveraines s'échappent vers le CDN.
4.4

Persistance — sea-orm + migrations

EngineV1
Quoi
Modèles typés, migrations-en-code, appliquées au démarrage.
Pourquoi
Schéma versionné, relisible, auto-appliqué ; pas de DDL manuel en prod.
N'est pas
Sûr contre la dérive par accident. Cicatrice : une colonne uuid liée comme String passait tous les tests SQLite et renvoyait 500 en Postgres (42804/42883) ; corrigé uuid→text. Vert-SQLite ≠ vert-Postgres.
4.5

Auth · commerce · identité de profil

EngineV1
Quoi
Auth JWT, résolution de profil, pont commerce BOBO (commandes, checkout, KYC, séquestre, marchand).
Pourquoi
C'est la moitié « dispose » — contexte vérifié + exécution qui valide avant que quoi que ce soit de réel n'arrive. Le bon domicile pour les futures actions proposées par l'IA.
N'est pas
De l'UX applicative — primitives agnostiques (le pont BOBO nommé est la seule couture délibérée).
4.6

Paiements

EngineV1 partiel
Quoi
Contrat normalisé + RailSelector + EventStore idempotent + routeur de webhooks. Wave réel (HMAC-SHA256) ; les autres renvoient RailNotConfigured.
Pourquoi
La fragmentation des paiements africains derrière un seul contrat ; webhooks idempotents.
Roadmap
bobo_checkout écrit les intentions en SQL brut — deux chemins à converger.
4.7

LiveKit — plan de contrôle temps réel

EngineV1 contrôle / ROADMAP média
Quoi
L'Engine émet des jetons + reçoit des webhooks ; le média circule client ↔ SFU. Non configuré → 503.
Pourquoi
L'Engine possède l'auth/contrôle, pas le chemin média (latence/coût/échelle).
N'est pas
Un serveur média.
4.8

Routeur IA en cascade

Harness (dans l'Engine aujourd'hui)V1 orchestration / ROADMAP inférence
Quoi
Routeur 5-tiers piloté par données (Tier 1 on-device → SiliconFlow → OpenRouter → HF) via reqwest. Gardes : disjoncteur · gate réseau · limiteur de débit · classification (FR/EN) · routage par sensibilité.
Pourquoi
Coût + souveraineté + résilience — le moins cher/local d'abord, le frontier en dernier ; prompts sensibles hors clouds tiers ; se dégrader, pas planter/dépenser. Providers interchangeables.
État
L'orchestration est réelle mais ne fait aucune inférence ; le Tier 1 est un placeholder (« …GGUF local en E7 ») ; sans clés → AllTiersExhausted. Domicile cible : Harness.
N'est pas
Un simple proxy — un routeur résilient, conscient des politiques et du réseau.
4.9

Search · Feed · Voix

Harness (dans l'Engine aujourd'hui)mixte
Search
V1 partiel /search + /index/upsert sur BGE-M3 + Qdrant ; profils canonical-1024 · edge-512/256/128. La pièce IA la plus réelle.
Feed
ROADMAP pipeline étagé sources→filters→scorers→hydrators→selectors — échafaudage.
Voix
ROADMAP sessions WebSocket, mock compatible PersonaPlex ; parole réelle derrière speech-core-sys (désactivé par défaut).
4.10

Capacités natives du Harness

HarnessROADMAP
Quoi
models · tools · memory · policy · evals · observability — contrats (Retriever, Ranker, PolicyEngine, ModelAdapter, RequestContext) + échafaudage/mocks. Le cerveau IA réutilisable que l'Engine appellera ; implémentations réelles promues hors R&D à mesure du durcissement.

05 Le programme de modèles VISION · R&D

Intelligence on-device/edge — stade recherche, pas en production. Le côté « propose » que l'Engine « dispose ». La conception n'est pas aléatoire : la couture texte (STT→texte→MT→texte→TTS) est préférée au S2ST opaque pour l'auditabilité ; des ancres réelles + ponts synthétiques avec porte de revue humaine comblent le manque de données ; le fossé de données wolof du commerce est l'avantage de long terme.

06 On-device — phase E7 ROADMAP

Voie A · côté engine

Inférence souveraine auto-hébergée

Combler le placeholder Tier-1 pour que les prompts Sovereign soient répondus sans quitter Diamniadio. Runtime : candle / llama-cpp-2 / mistral.rs / ort ; petit GGUF quantifié ; sous feature-flag ; budget RAM/CPU. Gain : l'inférence sensible ne touche jamais un cloud étranger.

Voie B · côté app

Vraie inférence côté téléphone

Un modèle sur l'appareil de l'utilisateur dans BOBO natif (ExecuTorch / MLC / llama.rn) — offline-first, le tier littéralement le moins cher ; l'Engine devient le repli cloud. Travail app, pas Engine. Là où atterrit LFM2.5-Audio.

08 L'inventaire V1 / Roadmap / Vision

Classement uniquement — la feuille de route détaillée est disséquée dans une passe de revue/inventaire séparée.

V1

Réel & livrable

  • Runtime Engine en ligne sur Railway : auth, profil, commerce/produits/commandes, persistance (DB privée), vérifié de bout en bout.
  • Types de souveraineté + stockage gardé par étiquette (garanti à la compilation).
  • Orchestration IA en cascade (a besoin de clés), recherche exécutable (sidecar+Qdrant), paiements Wave.
ROADMAP

Conçu / à suivre

  • SDK @yaatal/client → spin en une commande → create-yaatal-app.
  • Alignement Engine↔Harness (dépendance, dé-dup crates, promotion des capacités).
  • Tier-1 on-device (E7-A), feed, voix réelle, convergence paiements, LiveKit, verrou CORS, email/SMTP, build BOBO natif.
VISION

Conditionné recherche

  • Pile vocale-commerce souveraine wolof/français (voix → ASR → traduction → TTS → duplex).
  • Le fossé de données en langue peu dotée, qui se compose dans le temps.
  • SaaS multi-locataire, multi-région/PRA, « backend IA souverain pour les bâtisseurs africains ».

09 Les deux horloges — comment lire tout ce qui précède

Rapide · livrable maintenant

Horloge plateforme

Engine → SDK → spin → scaffold, qui se compose aujourd'hui. Utilise l'IA cloud prête-à-l'emploi pour la valeur produit à court terme. C'est le chemin le plus rapide.

Lente · haut plafond

Horloge recherche

Le programme de modèles wolof souverains. Dé-risquée dans le R&D Harness, promue seulement une fois durcie.

La lectureL'architecture (R&D Harness + règle de promotion) est littéralement conçue pour faire tourner les deux horloges sans les fusionner. Livrer la colonne sur l'horloge plateforme ; laisser le plafond arriver sur l'horloge recherche. Aujourd'hui : un projet de R&D doté d'une colonne de qualité production et d'une thèse de recherche défendable — une position rare et forte, tant que le cadrage reste honnête.
